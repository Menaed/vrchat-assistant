## 2026-08-17 · fix: MCP 服务端响应 ping 方法（长连接客户端 keepalive 挂起，issue #37）

- `f511e23` fix: MCP 服务端响应 ping 方法，修复客户端 keepalive 挂起超时（作者直推 main，issue #37 实测报告驱动，2026-08-17 01:19）
  - 现象：Hermes（MCP Python SDK，Streamable HTTP 传输）调用工具偶发挂起至 300s tool_timeout（实测 `get_weekly_report` 300.02s 超时）；**同刻 curl 直连 `:8799/mcp` 完全正常**（13.2s 返回）——排查迷惑点
  - 根因：`core/rpc-router.js` `handleRpc()` switch 只有 initialize / notifications/initialized / tools/list / tools/call 四个 case，`ping` 落 default → 返回空 SSE 响应（HTTP 200 + Content-Length: 0）；MCP Streamable HTTP 规范要求 ping 必须返回 `{"jsonrpc":"2.0","id":<原id>,"result":{}}`
  - 影响链：客户端 keepalive 每 ~3-4 分钟 ping（30s 超时）→ 等不到带匹配 id 的响应 → 判死重连 → 5 次连续失败进入 parked（300s 自检）→ parked 窗口内工具调用全部挂起；所有长连接客户端（官方 SDK / Hermes / Claude Desktop）受影响，一次性脚本/裸 curl 不受影响（新建连接直接 POST tools/call）
  - 修复：rpc-router.js 补 ping case 按协议返回 JSON-RPC 响应 + `core/http-server.js` 补 `DELETE /mcp` 路由（此前 SDK 终止会话 404：`Session termination failed: 404`）

**演进意义**：第一次暴露 MCP 协议合规性缺口——服务端此前只实现了业务方法（initialize/tools/*），协议级方法 ping 缺失让标准长连接客户端周期性判死重连、最终 parked 挂起至超时；确立两个模式：(1) 协议方法必须按规范返回带原 id 的 JSON-RPC result，空响应 = 客户端永远等不到结果；(2)「脚本/curl 直连正常 ≠ 长连接客户端正常」——排查 MCP 服务问题必须用长连接客户端复现，一次性连接会漏掉 keepalive / 会话生命周期类缺陷。
